明天不能直接接支付上线。密钥在仓库里、两个查询可以注入、结算没有互斥、金额用 `!==` 比较，这四条里任何一条都会在真钱上出事。

最少先改这五处：作废并移走写死的 `PAYMENT_KEY`、两处 SQL 改为参数化、结算先原子抢占 `pending` 再扣款、金额按分比较、全部接口加上调用方鉴权。日报时区和入参校验要同一批做完，不然上线当天的数是错的，负数金额也能打进支付。

## 问题 1：生产支付密钥写死在源码里
- **位置**：文件顶部 `PAYMENT_KEY`，约第 13 行
- **后果**：仓库、日志和外包交接包里都有一把 `sk_live_` 密钥。任何人拿到文件就能对 `api.pay.example.com` 发起真实扣款，而且轮换之前这把钥匙一直有效。
- **严重度**：致命
- **修法**：立刻作废这把钥匙，改为只从环境变量 `PAYMENT_KEY` 读取，进程启动时没有该变量就退出。

## 问题 2：按 id、按商户查订单使用字符串拼接 SQL
- **位置**：`GET /orders/:id` 约第 23 行；`GET /merchant/:merchantId/orders` 约第 33–35 行
- **后果**：`id` 或 `merchantId` 传入 `1 OR 1=1` 会读出别人的订单；node-pg 的简单查询允许多语句时，还可以带上删除语句。结算接口本身用了参数，但这两个读接口是开的。
- **严重度**：致命
- **修法**：两处都改成 `$1` 参数绑定，不要把路径参数拼进 SQL 文本。

## 问题 3：结算先查后扣，扣款和改状态不是一件事
- **位置**：`POST /orders/:id/settle` 约第 52–80 行，`chargeCustomer` 约第 83–106 行
- **后果**：两个并发请求都会读到 `status !== 'settled'`，各扣一次。扣款已成功但进程在 `UPDATE` 之前崩溃，或支付网关超时被 `catch` 吃掉，订单仍是 `pending`，重试再扣一笔。客户被多扣，对账对不上。
- **严重度**：致命
- **修法**：用 `UPDATE ... WHERE status = 'pending'` 原子改成 `charging`，只有抢到的请求去扣款；网关明确拒绝才改回 `pending`，网络不确定就停在 `charging`，禁止自动再扣。

## 问题 4：结算金额用浮点严格不等比较
- **位置**：`orderTotal` 约第 39–45 行；`settle` 里 `total !== row.expected_total` 约第 67 行
- **后果**：node-pg 对 NUMERIC 返回字符串，`120 !== "120"` 恒成立，正常订单全部 400，一笔都结不了。列若是浮点，`0.1` 一类二进制误差也会把本来相等的金额拒付。客户付不了款，或被误报金额不一致。
- **严重度**：致命
- **修法**：两边都换成整数分再比较，单价和数量先校验成有限正数。

## 问题 5：所有接口都没有鉴权
- **位置**：第 16 行之后的全部路由，没有任何校验中间件；`settle` 会调用 `chargeCustomer`
- **后果**：服务一旦能从外网访问，任何人可以拉全表订单，并对任意 `customer_id` 调用结算扣款。不需要先登录，也不需要是该商户。
- **严重度**：致命
- **修法**：用环境变量 `API_TOKEN` 校验 `Authorization: Bearer`，未通过一律 401。这只是上线前的门，不是完整账号体系。

## 问题 6：数据库连接没有等待，也没有错误处理
- **位置**：`db.connect()` 约第 11 行
- **后果**：监听端口已经打开时连接可能还没建立，头几笔请求直接失败。连接之后断掉时，Client 会抛未处理错误，进程死掉或一直假装还在服务。
- **严重度**：严重
- **修法**：`await db.connect()` 成功后再 `listen`，并监听 client 的 `error`。

## 问题 7：日报把 UTC 日期当成“今天”
- **位置**：`isToday` 约第 47–50 行；`GET /report/daily` 约第 127 行用它过滤
- **后果**：`toISOString()` 是 UTC。中国时间 0 点到 8 点，“今天”实际是 UTC 的昨天，当天上午的结算不会进日报，前一天晚上的会进。财务按这个数对账会对错一天。
- **严重度**：严重
- **修法**：按 `Asia/Shanghai` 的日历日在 SQL 里过滤，不要用 UTC 的日期字符串。

## 问题 8：日报遇到空的 settled_at 会整段 500
- **位置**：`GET /report/daily` 约第 127 行，`r.settled_at.toISOString()`
- **后果**：状态已是 `settled` 但 `settled_at` 为空（手工改数、旧数据、扣款路径写了一半）时，这里抛 TypeError，整个日报接口失败，当天对账停摆。
- **严重度**：一般
- **修法**：查询里排除 `settled_at IS NULL`，不要对空值调用 `toISOString`。

## 问题 9：日报先截断 5000 行再在内存里算今天
- **位置**：`GET /report/daily` 约第 124–128 行，`LIMIT 5000` 之后 `filter(isToday)`
- **后果**：当天结算超过 5000 笔时，更早的那些单被 LIMIT 丢掉，`count` 和 `sum` 少算。老板看到的日营收小于实际入账。
- **严重度**：一般
- **修法**：在 SQL 里按当天过滤并 `SUM`/`COUNT`，不要先截断再过滤。

## 问题 10：创建订单不校验商户、客户、单价和数量
- **位置**：`POST /orders` 约第 108–120 行；`orderTotal` 约第 39–45 行
- **后果**：缺 `customer_id` 的订单仍会入库，结算时向支付接口传空客户。`price` 为负或 `qty` 为负时总额为负，结算会向支付渠道提交一笔负数扣款。调用方可以造出不该存在的账。
- **严重度**：严重
- **修法**：拒绝缺少商户或客户的请求；单价、数量必须是有限数，单价不小于 0，数量必须大于 0。

## 问题 11：创建订单把完整请求体打进日志
- **位置**：`POST /orders` 约第 109 行，`console.log('create order', req.body)`
- **后果**：客户标识、商户和商品明细进了进程日志。日志被收集或外传时，这就是一份订单数据泄露。
- **严重度**：一般
- **修法**：删掉这行，不要打印请求体。

改动清单：作废写死的 `PAYMENT_KEY` 改为环境变量并要求 `API_TOKEN`；两处 SQL 拼接改为参数化；结算改为 `pending`→`charging`→`settled`，网关不明确成功时不退回 `pending` 以免再扣；金额按分比较并校验商户、客户、单价和数量；`await db.connect()` 且监听连接错误；日报改为 `Asia/Shanghai` 的 SQL 聚合，去掉 5000 行截断和空 `settled_at` 崩溃；删除创建订单时打印完整 body。
