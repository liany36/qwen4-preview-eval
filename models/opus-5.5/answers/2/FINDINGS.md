> **明天能不能直接上线？不能。** 现在接支付，等于把生产支付密钥公开，任何人都能拖走整库订单，还会出现重复扣款。
> **最少要改这几处才能上：** 问题 1（下线硬编码密钥并**立即作废轮换**）、问题 2 和 3（SQL 参数化）、问题 4（加鉴权并按商户隔离）、问题 5（价格以服务端为准）、问题 6 到 8（结算用原子状态位 + 幂等键，"结果未知"不能当失败处理）。
> 其余问题（9 到 13）可以上线后一周内修，但问题 9（未捕获异常会把进程打崩）建议一起修，改动只有几行。

## 问题 1：生产支付密钥硬编码在源码里
- **位置**：第 13 行 `PAYMENT_KEY = 'sk_live_...'`
- **后果**：任何拿到代码的人（外包团队、仓库协作者、日志或备份泄露）都能直接用这把 live key 调支付接口发起扣款或退款。外包已失联，这把 key 必须视为已泄露。
- **严重度**：致命
- **修法**：改为从环境变量或密钥管理服务读取，并在支付商后台**作废这把 key、重新签发**。只改代码不轮换等于没修。

## 问题 2：`GET /orders/:id` SQL 注入
- **位置**：第 23 行 `'SELECT * FROM orders WHERE id = ' + id`
- **后果**：请求 `/orders/1 OR 1=1` 就能拿到别人的订单；用 `1; DROP TABLE orders` 这类拼接甚至能改库或删库（pg 的简单查询协议允许多语句）。
- **严重度**：致命
- **修法**：改成 `$1` 参数化查询。

## 问题 3：`GET /merchant/:merchantId/orders` SQL 注入
- **位置**：第 34 行，`merchantId` 直接拼进 SQL
- **后果**：和问题 2 一样。任何人都能构造 merchantId 读出全部商户的订单，或者执行任意 SQL。
- **严重度**：致命
- **修法**：改成 `$1` 参数化查询。

## 问题 4：所有接口都没有鉴权，也没有按商户隔离
- **位置**：第 16、21、31、52、108、123 行，所有路由都没有认证中间件
- **后果**：任何人不登录就能 `GET /orders` 拖走全量订单（含客户 ID、商品、金额），能读取任意商户的订单，能对任意订单调用 `/settle` 触发扣款。`POST /orders` 的 `customer_id` 取自请求体，所以攻击者可以替任意客户建单，再调 `settle` 从受害者账户扣钱。
- **严重度**：致命
- **修法**：加认证中间件得到当前商户，所有查询和结算都带上 `merchant_id = 当前商户` 的条件。

## 问题 5：订单价格由客户端决定
- **位置**：`POST /orders`，第 110 到 118 行。`items[].price` 和 `qty` 直接取自 `req.body`，用来计算 `expected_total`
- **后果**：用户提交 `price: 0.01` 就能一分钱买任何东西；提交负数 `qty` 或 `price` 能造出负金额订单。之后 `settle` 的金额校验也只是拿同一份客户端数据重算一遍，形同虚设。
- **严重度**：致命
- **修法**：只接收商品 ID 和数量（数量校验为正整数），单价从服务端的商品表读取。

## 问题 6：结算存在并发竞态，会重复扣款
- **位置**：`POST /orders/:id/settle`，第 54 到 79 行。先 SELECT 判断 `status`，再扣款，最后 UPDATE，中间没有锁，也没有原子状态切换
- **后果**：用户双击支付按钮、前端超时重试或网关重放时，两个请求都读到 `pending`，都会调用 `chargeCustomer`，客户被扣两次。
- **严重度**：致命
- **修法**：扣款前用 `UPDATE ... SET status='charging' WHERE id=$1 AND status='pending' RETURNING` 原子地抢占这笔订单，只有抢到的请求才能扣款。

## 问题 7：调用支付接口时没有带幂等键
- **位置**：`chargeCustomer`，第 85 到 97 行，请求头里没有 Idempotency-Key
- **后果**：只要同一订单被重试（见问题 6、问题 8），支付商就会把每次请求都当成一笔新扣款。`reference` 只是备注字段，不保证去重。
- **严重度**：严重
- **修法**：请求头加上以订单号为基础的 `Idempotency-Key`，让支付商侧去重。

## 问题 8：支付结果未知时被当成失败处理
- **位置**：`chargeCustomer`，第 98 到 105 行。超时、网络断开、5xx 或非 JSON 响应都被 `catch` 吞掉，返回 `null`。`fetch` 也没有设置超时
- **后果**：请求已经到达支付商并扣款成功，但响应在回程中丢失时，服务返回 502 "charge failed"，订单仍是 `pending`。用户或客服再点一次，就会再扣一次。没有超时还会让请求无限挂起。
- **严重度**：严重
- **修法**：区分"明确失败"和"结果未知"两种情况。未知时把订单留在 `charging` 状态等待对账或回调确认，不允许直接重试；同时给请求加超时。

## 问题 9：异步路由没有错误处理，一个坏请求就能打崩进程
- **位置**：所有 `async (req, res) => {...}` 路由（Express 4 不会捕获被 reject 的 promise）
- **后果**：任何数据库报错，例如请求 `/orders/abc` 触发 SQL 语法错误，都会变成 unhandledRejection。Node 15 及以上版本默认直接退出进程，任何匿名用户都能一条请求让整个服务宕机。
- **严重度**：严重
- **修法**：用包装函数把 rejection 交给 `next(err)`，再加一个统一的错误中间件返回 500。

## 问题 10：整个服务只有一个数据库连接，断了不会重连
- **位置**：第 10 到 11 行 `new Client(...)`，`db.connect()` 既没有 await，也没有错误处理
- **后果**：所有请求在同一条连接上串行执行，高峰期会排队。数据库重启或网络抖动后，连接对象会触发未处理的 `error` 事件，导致进程崩溃，或者之后所有查询都失败，直到有人手动重启服务。
- **严重度**：严重
- **修法**：换成 `pg.Pool` 并监听 `error` 事件。

## 问题 11：金额用浮点或字符串参与计算和比较
- **位置**：`orderTotal` 第 42 行；`settle` 第 67 行 `total !== row.expected_total`；`/report/daily` 第 128 行 `acc + r.expected_total`
- **后果**：如果 `expected_total` 是 `NUMERIC` 列（金额通常用这个类型），pg 会返回**字符串**。这时 `!==` 永远成立，**所有订单都会因为 amount mismatch 无法结算**；日报里的加法会变成字符串拼接，得到 `"0199.00250.00"` 这种结果。如果是 float 列，`19.9 * 3` 这类计算会有精度误差，导致对不上账。
- **严重度**：严重
- **修法**：全链路统一用整数"分"表示金额，比较前显式转成 Number 或 BigInt。

## 问题 12：日报的"今天"按 UTC 算，不是北京时间
- **位置**：`isToday` 第 48 行 `new Date().toISOString()`
- **后果**：服务在东八区运营，日报统计的实际是北京时间 08:00 到次日 08:00 的窗口。财务拿这份日报和支付商的自然日账单对账，每天都会对不上，0 到 8 点的订单会被算进前一天。
- **严重度**：严重
- **修法**：在 SQL 里按 `Asia/Shanghai` 时区计算当天的起止时间。

## 问题 13：日报先取最近 5000 条再在内存里过滤
- **位置**：`/report/daily` 第 125 到 127 行 `LIMIT 5000` 加 JS 端 `filter`
- **后果**：当天结算超过 5000 单时，日报会少算，而且没有任何提示。每次请求还会把 5000 行完整订单拉进内存。
- **严重度**：一般
- **修法**：用 SQL 的 `WHERE settled_at` 范围条件加 `count` / `sum` 直接聚合。

**patched/orders.js 改动清单**：密钥改为读环境变量（问题 1）；两处 SQL 参数化（问题 2、3）；加 `requireMerchant` 鉴权并给所有查询加商户条件（问题 4）；建单时价格改从 `products` 表读取，并校验数量（问题 5）；`settle` 改为 `pending→charging` 原子抢占（问题 6）；支付请求加 `Idempotency-Key`（问题 7）；`chargeCustomer` 区分 succeeded / failed / unknown 三种结果并加 10 秒超时，unknown 时订单保留为 charging（问题 8）；加 `wrap` 和错误中间件（问题 9）；`Client` 换成 `Pool`（问题 10）；金额比较前转 Number，日报在 SQL 里聚合（问题 11）；日报按 Asia/Shanghai 时区计算（问题 12、13）；删除打印完整请求体的日志。

**patched 里的假设**：`products(id, merchant_id, price_fen)` 表存在；鉴权暂用环境变量 `API_TOKENS` 配置 token 到商户的映射，正式环境应接入现有的账号体系；日报因此改成只统计当前商户的数据，如果财务需要全平台汇总，应另开一个管理员接口；`charging` 状态的订单需要配一个对账任务（按幂等键向支付商查询结果），这个任务没有写。
